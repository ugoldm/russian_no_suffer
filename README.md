## Локальная демонстрация

Нужен Node.js **24** (используется встроенный SQLite).

```sh
npm install
npm run dev
```

Откройте [приложение](http://127.0.0.1:5173/). Нажмите «Открыть демонстрационный кабинет». Нажмите «Поделиться ссылкой» в карточке теста и откройте полученную ссылку в другой вкладке. Выполните работу, затем в кабинете откройте «Результаты» → «Обновить».

Локальный API слушает только `127.0.0.1:5174`. Данные хранятся в `.local/demo.sqlite` и переживают перезапуск. Ключи находятся на сервере, а не в браузере. Кабинет в деморежиме доступен без проверки личности — используйте только тестовые данные. Вход ученика и кабинет преподавателя используют разные сессии, поэтому их можно проверять в одном браузере.

При `npm run dev` и `npm run dev:api` локальный API автоматически перезапускается после изменения серверного кода. После перезапуска нажмите «Обновить» в результатах или обновите страницу, чтобы получить актуальные данные.

**Локальная ссылка работает только на этом компьютере.** Для учеников на других устройствах необходимы Supabase и опубликованный frontend. Статическая сборка в деморежиме без локального API не является работающим общим сервисом. Демо-API не разворачивать в интернете.

## Подключить Supabase

### 1. Создать проект и применить миграции

Создайте проект в Supabase. Для новой пустой базы подготовьте один установочный файл:

```sh
npm run supabase:setup
```

Откройте `imports/setup/supabase-init.sql`, скопируйте всё содержимое в Supabase SQL Editor и нажмите **Run** один раз. Файл объединяет миграции по порядку в одну транзакцию: ошибка отменяет всю установку. Повторная установка в уже настроенную базу блокируется. Генератор работает локально, не подключается к Supabase и не требует ключей. Он не настраивает Auth, преподавателя или реальные тесты — эти шаги описаны ниже.

Отдельные миграции остаются историей изменений и способом обновлять существующую базу. Вместо установочного файла их можно выполнить по порядку:

1. `supabase/migrations/001_initial.sql` — закрытые таблицы, права и серверные функции.
2. `supabase/migrations/002_demo_test.sql` — первый демонстрационный тест.
3. `supabase/migrations/003_direct_test_links.sql` — прямые ссылки на тесты, удаление групп и домашних заданий с сохранением попыток.
4. `supabase/migrations/004_attempt_duration.sql` — время прохождения от нажатия «Начать» до отправки ответов.
5. `supabase/migrations/005_hide_results.sql` — сохраняемое скрытие и восстановление работ в кабинете преподавателя.
6. `supabase/migrations/006_unread_results.sql` — серверное состояние просмотренных результатов и счётчик новых прохождений.
7. `supabase/migrations/007_student_group.sql` — обязательный выбор группы для новых работ, проверка расписания и сохранение группы в результатах.
8. `supabase/migrations/008_exam_group_schedule.sql` — отдельные расписания ОГЭ и ЕГЭ, серверная проверка по экзамену теста с сохранением групп прежних работ.
9. `supabase/migrations/009_remove_friday_group.sql` — исключение пятницы из выбора новых групп с сохранением прежних работ и начатых черновиков.
10. `supabase/migrations/010_digit_set_answers.sql` — проверка текстовых наборов цифр в любом порядке по явному правилу `normalization.digitSet`.
11. `supabase/migrations/011_grouped_tasks.sql` — общие тексты с несколькими заданиями, независимый балл за каждый ответ и рекурсивное скрытие ключей до отправки.
12. `supabase/migrations/012_required_answers.sql` — запрет сдачи с пропусками, включая задания внутри общего текста; прежние результаты и повторные запросы сохраняются.
13. `supabase/migrations/013_archive_ege_4_demo.sql` — убрать демонстрационный ЕГЭ № 4 из каталога и запретить новые прохождения, сохранив работы и начатые черновики.

Чтобы убрать тестовый ЕГЭ № 4 из уже настроенного Supabase с миграциями 001–012, выполните содержимое `supabase/migrations/013_archive_ege_4_demo.sql` в SQL Editor и обновите кабинет. Повторное выполнение безопасно. Архивируются все версии только теста `ege-4-demo`; другие тесты не затрагиваются. Старая ссылка показывает архивный тест без возможности начать новую работу; ранее начатые работы можно завершить, сохранённые результаты доступны ученику и преподавателю. Пересборка сайта не требуется. Это подготовленный SQL: его наличие в проекте само по себе не меняет удалённую базу или локальную SQLite-базу.

Демонстрационный тест без владельца требует единственного разрешённого преподавателя для новых попыток. Импортированные тесты всегда привязаны к владельцу.

Миграция 001 выполняется один раз на новой базе. Миграция 002 повторяема и не перезаписывает опубликованную версию. Вся информация хранится в схеме `private`: не добавляйте её в список exposed schemas и не предоставляйте прямые права клиентам.

Для существующей базы выполните только ещё не применённые миграции по порядку: 003, 004, 005, 006, 007, 008, 009, 010, 011, 012, 013. Локальная SQLite-база обновляется автоматически при перезапуске API; все работы и прежние активные ссылки сохраняются. SQL-миграции также сохраняют активные прежние ссылки и исходные ответы; миграция 013 запрещает новые прохождения демонстрационного ЕГЭ № 4.

Время прохождения каждой попытки показывается в таблице результатов, деталях работы и результате ученика. Отсчёт идёт после нажатия «Начать тест» до успешной отправки, включая перерывы; ввод имени не учитывается. Обновление страницы не сбрасывает отсчёт. Новая попытка начинает отсчёт заново после нажатия «Начать тест». Для прежних работ длительность вычисляется по сохранённым серверным датам начала и отправки. Если дат нет, показывается «Не записано».

При следующем изменении базы добавляйте новую миграцию, не переисполняйте 001 и не очищайте результаты.

В результатах преподаватель может нажать «Скрыть» у ненужной работы. Она исчезает из основного списка и его счётчиков; сразу после скрытия доступно «Отменить». В списке «Скрытые» можно открыть ответы или нажать «Вернуть». Видимость сохраняется на сервере и после обновления страницы. Время отправки, оценка, ответы и результат ученика не изменяются; восстановленная работа занимает место по своей исходной дате отправки. Фильтры по экзамену, тесту и имени работают в обоих списках. В Supabase менять видимость может только преподаватель, которому принадлежит работа.

Сводка над таблицей показывает количество прохождений, среднюю долю верных ответов и среднее время для текущего списка работ. Она учитывает выбранные экзамен, тест, имя и видимость. Средняя доля считается по исходным долям «правильные/всего» с равным весом каждого прохождения и округлением итогового процента. Среднее время округляется до секунды; работы без записанного времени исключаются из его расчёта, рядом показывается число работ с записанным временем. Пустой список показывает 0 прохождений и «—» вместо средних значений.

Значок у пункта «Результаты» показывает новые непросмотренные прохождения, исключая скрытые работы. Открытие результатов через меню или карточку теста отмечает загруженные работы просмотренными независимо от фильтров. В открытой видимой странице новые загруженные работы также считаются просмотренными. При нуле значок отсутствует. Состояние хранится на сервере, сохраняется после перезагрузки и синхронизируется между устройствами преподавателя при обновлении. Кабинет обновляет данные каждые 30 секунд в видимой вкладке и при возврате в неё. Миграция 006 считает прежние работы просмотренными; новые успешные отправки создают уведомления. Повторный запрос сохранённой отправки не создаёт уведомление повторно. Ученики и другой преподаватель не могут менять это состояние; отметка подтверждается только для конкретных загруженных ID, так что позднее поступившие работы остаются новыми.

### 2. Настроить вход

В разделе Authentication:

- Включите **Anonymous Sign-Ins** для учеников.
- Создайте постоянного пользователя преподавателя с email и паролем (через Dashboard), включив **Auto Confirm User**. Публичная регистрация преподавателей в приложении отсутствует. Если аккаунт уже создан с паролем и подтверждённым email, используйте его — новый UUID не нужен.
- Скопируйте ID этого пользователя и выполните:

```sql
insert into private.teachers(user_id)
values ('UUID_ПОЛЬЗОВАТЕЛЯ_ПРЕПОДАВАТЕЛЯ')
on conflict do nothing;
```

Замените placeholder настоящим UUID. Наличие аккаунта без этой записи не даёт доступа к кабинету.

Для входа преподавателя используются **email и пароль**, без писем и почтовых кодов. Frontend вызывает `signInWithPassword`; пароль проверяет Supabase Auth. Email аккаунта подтверждается администратором при создании через **Auto Confirm User**; отключать подтверждение email для всего проекта не требуется. Для этого способа входа настройка SMTP и шаблонов писем не нужна. Восстановление пароля через письмо в приложении отсутствует. Настройки Site URL/Redirect URLs должны соответствовать локальному и опубликованному доменам.

Настройте защиту от массового создания анонимных пользователей: Supabase поддерживает CAPTCHA, в том числе Turnstile. Включите её на стороне Supabase, укажите секретный ключ **только в Dashboard**, разрешите домены приложения в Turnstile, а публичный site key передайте в `VITE_TURNSTILE_SITE_KEY`. Если защита включена в Supabase, но ключ frontend отсутствует, анонимный вход будет отклонён. Проверьте квоты и лимиты входа для ожидаемого количества учеников.

### 3. Настроить frontend

Скопируйте `.env.example` в `.env.local` и заполните публичные настройки:

```dotenv
VITE_APP_MODE=supabase
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
VITE_TURNSTILE_SITE_KEY=YOUR_PUBLIC_SITE_KEY_IF_ENABLED
VITE_BASE_PATH=/
```

`.env.local` исключён из Git. **Не используйте secret key или service_role вместо publishable key.** Любое значение `VITE_*` будет видно в браузере.

Запустите `npm run dev`: в режиме Supabase запросы идут в общую базу; локальный демо-API не используется. Никакого автоматического перехода на демонстрационные результаты при ошибке Supabase нет.

Пройдите контрольный сценарий: вход преподавателя → библиотека → ссылка на тест → работа в другом браузере → одинаковый результат ученика и преподавателя.

### GitHub Pages

Перед использованием учтите ограничения Pages для онлайн-бизнеса/коммерческого SaaS, описанные в [официальных условиях](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). ## Импорт следующих материалов

Передайте файл агенту в чат. Он извлечёт упражнения и ключи, покажет отчёт и создаст JSON по форме `server/demo-content.mjs` (объект теста). Рабочие исходники кладите в `materials/`, подготовленные данные и SQL — в `imports/`: оба каталога исключены из Git.

Для проверки JSON и подготовки SQL:

```sh
npm run import:sql -- materials/test.json UUID_ПРЕПОДАВАТЕЛЯ imports/test.sql
```

Команда не обращается к сети и не требует секретов. Она проверяет ID, формат, ключи, варианты и правила нормализации. SQL содержит ключи, поэтому сохранение разрешено только в `imports/`. Выполните его в закрытом SQL Editor после просмотра содержания.

Поля теста: `id` (один на экзамен/год/номер/тему), `versionId` (новый для каждой версии), `exam`, `year`, `taskNumber`, `title`, `subtitle`, `version`, `status`, `demo`, `description`, `source`, `exercises`. Тема — согласованное уточнение после номера в каноническом названии, например «Запятые» или «Тире и двоеточие» у № 21; без уточнения тема общая. Разные темы имеют отдельные ID, версии, ссылки и результаты; дублирование одной темы под разными ID отклоняется локальным и SQL-импортом. Необязательное `estimatedDuration` задаёт ориентировочное время набора (например, «20–30 минут»), одинаковое в каталоге и на старте.

Для добавления проверенного набора в локальное приложение запустите API, затем:

```sh
npm run import:local -- imports/test.json
```

Команда атомарно добавляет версию в `.local/demo.sqlite`, сохраняет прежние ссылки и попытки и не создаёт дубликат при повторном запуске. Статус берётся из JSON: `draft` недоступен ученикам и не отображается в библиотеке; после подтверждения содержания владельцем можно изменить его на `published` и повторить команду. Публикация допускается только для идентичного черновика с ключами. Изменённое содержание требует новой версии. Обновите страницу кабинета после импорта. Контент и ключи остаются в исключённых из Git каталогах и локальной базе; локальный импорт не публикует тест в интернете.

## Проверки

```sh
npm test
npm run test:db
npm run build
```

`npm test` проверяет серверное оценивание, пропуски, идемпотентность, чужие попытки, прямые ссылки, архивирование тестов и миграцию старых данных, импорт и сохранение SQLite после перезапуска. HTTP-тесту нужна возможность слушать локальный порт.

Проверка парольного входа использует настоящий клиент Supabase с подменёнными ответами Auth: проверяет ошибки входа, передачу CAPTCHA, сохранение пробелов в пароле и разделение сессий преподавателя и ученика. Реальные аккаунты и работы при этом не затрагиваются.

`npm run test:db` применяет **настоящие SQL-миграции** к PostgreSQL в PGlite с тестовыми заменами `auth.uid()`/`auth.jwt()`, переключает роли и проверяет права, ключи, проверку, идемпотентность и неизменяемость версий. Этот тест не заменяет контрольного прохода в реальном Supabase: Auth, CAPTCHA и сетевую конфигурацию провайдера можно проверить только после его подключения.

Дополнительная браузерная регрессия перехода к результатам:

```sh
node tests/student-transition.browser.mjs
```

Требует установленного Playwright и Chromium. Если они доступны через внешний runtime, задайте `PLAYWRIGHT_MODULE` (путь к модулю Playwright) и `BROWSER_EXECUTABLE` (путь к браузеру). Проверка создаёт отдельную временную SQLite-базу с синтетическими заданиями и локальный frontend, моделирует замену текстовых узлов браузерным переводчиком, сетевую ошибку отправки, показ результата без перезагрузки, восстановление и новое прохождение на четырёх размерах окна. Рабочую базу не использует; скриншоты сохраняются в `.local/student-transition/`.

## Данные и ограничения

Имя не подтверждает личность. Сессия ученика сохраняется в этом браузере; другой браузер или устройство создаёт другого технического пользователя. На общем устройстве нажмите «Другой ученик». Одинаковые имена не объединяют владельцев попыток. Ссылка ведёт на конкретную версию теста; её можно переслать.

Результаты хранятся без автоматического удаления до решения владельца о сроке хранения. Для удаления конкретной работы по запросу сначала проверьте её ID и владельца в закрытой базе, затем удалите только соответствующую строку `private.attempts`; не удаляйте пользователя Auth с чужими/нужными работами. Все ответы этой попытки хранятся в самой записи. Не делайте такого удаления без явного указания владельца.
